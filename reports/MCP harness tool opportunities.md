# Control Surfaces Should Lead Mcptools Growth

**Executive conclusion — October 7, 2026.** The best MCP servers do not win by exposing the most operations; they help a harness select a small capability set, keep bulk data outside model context, make authority explicit, and expose failures as structured evidence. mcptools already implements the two most repeated ideas—progressive discovery and sandboxed code-mode composition—so copying another tool finder, dispatcher, or JavaScript executor would add little value. Its highest-value next additions are bounded code search, universal output budgets, readiness diagnostics, preflight validation, bounded repository evidence, and redacted call traces. **Start with `atlas_search`: it closes a clear local workflow gap, reuses the current SQLite/tree-sitter stack, stays read-only, and has a much smaller security surface than federation, shell execution, or durable result storage.** The broader roadmap should extend mcptools as a curated harness control plane, not turn it into a generic MCP gateway.

## Strong evidence favors interaction contracts, not popularity rankings

The evidence combines four independently researched views: official MCP specifications and directories, public repository/package signals, community discussions and implementations, and the local mcptools codebase. The sources agree on three transferable patterns: **progressively disclose tools, bound or defer large results, and make permissions and state transitions explicit**. The main correction from local inspection is important: ecosystem research recommends a discovery facade and code-mode execution, but mcptools already has both. Full mode exposes 77 registered tools; discovery mode exposes `find_tools` and `call_tool`; code mode adds `execute`, while unlisted tools remain dispatchable ([`registered_tools()` and registry tests, `crates/mcptools/src/mcp/tools/mod.rs:1045-1129,1262-1423`](../crates/mcptools/src/mcp/tools/mod.rs#L1045-L1129); [mode filtering, `crates/mcptools/src/mcp/tools/mod.rs:797-870`](../crates/mcptools/src/mcp/tools/mod.rs#L797-L870)). `execute` already provides limited QuickJS composition with separate Write and Spend opt-ins ([`crates/mcptools/src/mcp/tools/execute.rs:5-84`](../crates/mcptools/src/mcp/tools/execute.rs#L5-L84)).

Evidence quality is uneven. GitHub stars and forks measure attention and contributor interest, not active use. Package downloads are closer to execution but include CI, mirrors, updates, and repeated `npx` or `uvx` runs. No source established unique active users, retention, production deployments, or successful call counts. Current releases plus package traffic therefore provide a useful maintenance/adoption signal, but not market share. Capability claims come mainly from official specifications, tool references, and project documentation; vendor token-reduction figures and community reports are directional, not independent benchmarks. Official directory presence proves discoverability, not safety: the MCP Registry remains preview and delegates curation and security enrichment to downstream services ([MCP Registry trust model](https://modelcontextprotocol.io/registry/about#trust-and-security)).

The official July 2026 protocol also creates a timing limitation. It standardizes live discovery, cache metadata, structured outputs, explicit state handles, tasks, and request-scoped authorization, while mcptools advertises MCP `2025-06-18` and still handles `initialize` over stdio/SSE ([MCP 2026-07-28 changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog); [`crates/mcptools/src/mcp/mod.rs:61-128`](../crates/mcptools/src/mcp/mod.rs#L61-L128)). That is a real interoperability gap, but it is a separate protocol/transport program, not a reason to distort the tool roadmap. No material conflict appeared among the four note sets beyond this version boundary and the already-implemented discovery/composition recommendations.

These examples reinforce a server-side constraint reported by users: once an MCP response enters model history, a later hook cannot recover the spent context. Large-result control must happen in the server or proxy response path ([HN empirical report](https://news.ycombinator.com/item?id=47193074)). ## Eight additions rank above broader federation

The ranking weights direct harness value and architectural fit above raw ecosystem popularity. Cost and risk are relative engineering assessments based on the current static registry, typed `schemars` models, functional-core split, installed dependencies, and central dispatch ([core boundary, `crates/core/src/lib.rs:1-45`](../crates/core/src/lib.rs#L1-L45); [dependencies, `Cargo.toml:31-68`](../Cargo.toml#L31-L68); [registry/dispatch duplication, `crates/mcptools/src/mcp/tools/mod.rs:164-794,873-1018`](../crates/mcptools/src/mcp/tools/mod.rs#L164-L794)).

| Rank | Concrete addition | User value | Strategic fit | Cost | Evidence | Key risk |
|---:|---|:---:|:---:|:---:|:---:|---|
| **1** | **`atlas_search`** with bounded symbol/path/text modes | High | High | Low–medium | Medium–high | Stale indexes or broad text matches can create misleading/noisy evidence. |
| **2** | **Universal output budgets and continuation/result handles** for large structured reads | High | High | Medium–high | High | Handle authorization, expiry, storage growth, and exact-result integrity add lifecycle complexity. |
| **3** | **`mcptools_doctor`** for mode/version, enabled domains, non-secret credential presence, external binaries, Atlas health, and lane policy | High | High | Low–medium | Medium–high | Diagnostics can leak paths, account identity, or secret-derived detail unless fields are explicitly safe. |
| **4** | **`validate_tool_call`** for schema, ToolKind, and required permission without dispatch | Medium–high | High | Low | High | Validation can drift from real dispatch unless both use one canonical path. |
| **5** | **`repo_status` / `repo_diff_summary`** with changed files, staging state, ahead/behind, and diffstat only | High | High | Medium | Medium | Repository boundary bypasses and unbounded diffs; reuse lane canonicalization and subprocess caps. |
| **6** | **`tool_call_trace`** with opt-in redacted tool, kind, duration, status, error class, and byte counts | Medium–high | High | Medium | Arguments, results, and error text can contain secrets; do not retain them by default. |
| **7** | **Catalog profiles** with operator domain/tool allowlists and read-only status | Medium | Medium–high | Medium | Profiles can be mistaken for authorization; deny/read-only rules must override inclusion. |
| **8** | **Structured `call_tools`** for bounded sequential/parallel calls | Medium | Medium | Low–medium | It duplicates `execute` for capable clients and can multiply output or write effects. |

`atlas_search` ranks first because Atlas currently exposes only tree browsing, path/symbol summaries, and health; search is absent from the registered surface ([Atlas registrations, `crates/mcptools/src/mcp/tools/mod.rs:528-550`](../crates/mcptools/src/mcp/tools/mod.rs#L528-L550)). It reuses existing SQLite, tree-sitter, glob, and ignore dependencies, and the external evidence from Serena and budgeted structural-code tools supports semantic, bounded retrieval. Universal budgeting ranks second because only five large tools currently support dotted `fields`, while the server-wide need is strongly evidenced ([projection implementation, `crates/core/src/projection.rs:6-91`](../crates/core/src/projection.rs#L6-L91); [projection contract, `CONTEXT.md:237-261`](../CONTEXT.md#L237-L261)). A first increment should standardize item/byte limits and truncation metadata; opaque exact-result handles should follow only after lifecycle and authorization rules are designed.

The next tier improves setup and safe execution. `mcptools_doctor` consolidates readiness that is now fragmented across domain tools. `validate_tool_call` can reuse the installed JSON Schema validator and centralized schemas ([`call_tool` validation path, `crates/mcptools/src/mcp/tools/call_tool.rs:37-75`](../crates/mcptools/src/mcp/tools/call_tool.rs#L37-L75)). Bounded Git status/diff tools should reuse the lane allowlist and canonical-path checks rather than forward arbitrary flags ([lane safety contract, `.claude/context/lanes.md:3-43`](../.claude/context/lanes.md#L3-L43)). Call traces align with OpenTelemetry propagation in MCP 2026 and gateway practice, but metadata-only tracing is the safe first boundary ([MCP observability changes](https://modelcontextprotocol.io/specification/2026-07-28/changelog); [mcp-agent observability](https://docs.mcp-agent.com/mcp-agent-sdk/advanced/observability)).

## Defer duplicates, CRUD expansion, and unsafe breadth

Do not add another progressive finder, named dispatcher, JavaScript orchestration tool, generic Linear dependency graph, PR-comment tool, lane allocator, or basic output projection. mcptools already has these capabilities across `find_tools`, `call_tool`, `execute`, the Linear/Bitbucket surfaces, lane tools, and five projected readers ([catalog and composition, `CONTEXT.md:47-107,149-187`](../CONTEXT.md#L47-L107); [current external-service registrations, `crates/mcptools/src/mcp/tools/mod.rs:190-423`](../crates/mcptools/src/mcp/tools/mod.rs#L190-L423)). Structured `call_tools` is justified only as a compatibility path for clients that cannot safely emit JavaScript.

Defer more app-specific Jira, Confluence, Bitbucket, or Linear CRUD unless a concrete workflow gap appears. Popular servers show that breadth alone is not the transferable advantage; validation, discovery, output shaping, and recovery are. Also defer downstream MCP federation, container/Kubernetes runtime management, multi-tenant auth, an OAuth broker, admin UI, and REST/gRPC translation. Those features are central to MetaMCP, ToolHive, Docker Gateway, and ContextForge, but they would change mcptools from a curated static server into a gateway with dynamic transports, name collisions, policy persistence, and lifecycle supervision that its architecture does not contain ([MetaMCP](https://github.com/metatool-ai/metamcp/blob/ai-dev/README.md); [ContextForge](https://github.com/IBM/mcp-context-forge/blob/main/README.md); [`crates/mcptools/src/mcp/mod.rs:40-65`](../crates/mcptools/src/mcp/mod.rs#L40-L65)).

Avoid arbitrary shell/test execution, unconstrained browser code, automatic lane delete/merge/push, and default LLM summarization. Generated code moves risk rather than removing it; Playwright calls arbitrary browser code RCE-equivalent, and Anthropic requires sandbox, network, filesystem, secret, CPU, and time controls ([Anthropic code-mode guidance](https://www.anthropic.com/engineering/code-execution-with-mcp); [Playwright MCP guide](https://playwright.dev/docs/getting-started-mcp)). Lossy summarization without exact retrieval can hide constraints. Durable memory, task DAGs, and multi-agent locks are useful only when mcptools owns that lifecycle; adding them now would create context and state costs without evidence that this server should become the system of record. Streamable HTTP and the 2026 protocol revision should be tracked separately as interoperability work.

## First ticket: add bounded Atlas search

**Scope.** Add one read-only `atlas_search` tool over the existing Atlas index. Accept a query, a required search mode (`symbol`, `path`, or `text`), and a capped result limit. Return deterministic structured matches with only the minimum locating evidence: path, symbol/kind when available, line or range when available, and a bounded snippet. Keep deterministic shaping in `mcptools_core` and index I/O in `mcptools`. Add no dependency, subprocess, write behavior, or automatic index mutation.

**Acceptance criteria.** The tool appears in the registry, dispatcher, domain listing, and contract oracle with Read annotations and generated input/output schemas. Each mode returns deterministic ordering, enforces a hard maximum result count and snippet size, and represents no matches as a valid empty result. Missing or stale index state produces an actionable structured error rather than silently scanning the repository. Tests cover symbol, path, and text matches; limit enforcement; invalid mode/input; no-match behavior; index-unavailable behavior; structured/text output parity; and existing code-mode schema-token caps. The implementation follows the current core/shell split and does not weaken Atlas workspace boundaries.

**Why first.** This is the smallest high-value gap with direct daily harness utility. It extends an existing domain using installed infrastructure, needs no credentials or persistent state, and cannot mutate user work. It also creates a concrete test bed for the second-ranked output-budget contract without first committing mcptools to a generic result store.
